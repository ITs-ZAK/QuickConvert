# QuickConvert v0.2.0 Release Design

## Cel

Opublikować aktualny stan `main` jako nowe wydanie GitHub `v0.2.0`, zawierające przeprojektowany interfejs, branding QuickConvert i funkcjonalne ustawienia konwersji. Nie zmieniać ani nie podmieniać assetów istniejącego wydania `v0.1.0`.

## Wersja i nazwy

- Wersja produktu: `0.2.0`.
- Tag Git: `v0.2.0`.
- Nazwa GitHub Release: `QuickConvert v0.2.0`.
- Instalator: `QuickConvert-0.2.0-win-x64-setup.exe`.
- Wersja w `Directory.Build.props` i `installer/QuickConvert.iss` musi być identyczna.

## Branding instalatora

- `SetupIconFile` pozostaje ustawione na `assets/branding/quickconvert.ico`.
- Instalator, pasek zadań, lista aplikacji i deinstalator mają używać logo QuickConvert zamiast domyślnej ikony pobierania.
- `WizardSmallImageFile` pozostaje ustawione na `assets/branding/quickconvert-wizard-small.png`.
- Test kontraktu wydania sprawdza wersję, nazwę instalatora, ikonę setupu i ikonę deinstalatora.

Zrzut użytkownika pochodzi ze starego assetu `v0.1.0`, opublikowanego przed integracją brandingu. Nowy instalator musi zostać zbudowany z tagu wskazującego aktualny `main`.

## Automatyzacja GitHub Release

Istniejący workflow `.github/workflows/release.yml` pozostaje jedyną ścieżką publikacji. Push tagu `v0.2.0` uruchamia build na `windows-latest`, testy .NET z FFmpeg, testy rozszerzeń, budowę instalatora i utworzenie GitHub Release.

Konfiguracja `softprops/action-gh-release` otrzymuje:

- nazwę `QuickConvert v0.2.0` wyprowadzoną z tagu;
- automatyczne release notes;
- instalator Windows;
- `SHA256SUMS.txt`;
- XPI Firefoksa, jeśli workflow je wygeneruje.

Nie publikować ręcznie lokalnego pliku i nie używać `gh release create` jako podstawowej ścieżki. Dzięki temu release pochodzi z odtwarzalnego, testowanego buildu CI.

## Przepływ publikacji

1. Zmienić wersję na `0.2.0` w obu źródłach wersji.
2. Dodać test spójności wersji i brandingu instalatora.
3. Uruchomić pełne testy, build i lokalny build release.
4. Zatwierdzić zmiany i wypchnąć `main`.
5. Utworzyć opisany tag Git `v0.2.0` (`git tag -a`) na zweryfikowanym commicie i wypchnąć tag.
6. Poczekać na zakończenie workflow Release.
7. Sprawdzić przez publiczne GitHub API tag, nazwę, commit i listę assetów.
8. Pobrać lub odczytać metadane instalatora z release i potwierdzić opublikowaną sumę SHA-256.

## Obsługa błędów

- Jeśli testy lub lokalny build nie przejdą, nie tworzyć tagu.
- Jeśli push `main` nie będzie fast-forward, zatrzymać publikację i wyjaśnić rozbieżność.
- Jeśli workflow GitHub Actions zakończy się błędem, nie tworzyć ręcznego zastępczego release; naprawić workflow lub kod, a tag przenieść wyłącznie po jawnej zgodzie użytkownika.
- Jeśli brakuje sekretów AMO, release może zawierać niepodpisane XPI zgodnie z obecnym zachowaniem workflow, ale instalator Windows nadal musi zostać opublikowany.
- Jeśli instalator lub `SHA256SUMS.txt` nie pojawi się w assetach, wydanie nie jest uznawane za ukończone.

## Testy i kryteria odbioru

- Wszystkie testy .NET, w tym integracja z prawdziwym FFmpeg, przechodzą.
- Build rozwiązania kończy się z zerem błędów i ostrzeżeń.
- Testy i sprawdzanie składni rozszerzeń Chrome/Firefox przechodzą.
- Lokalny build tworzy `QuickConvert-0.2.0-win-x64-setup.exe`.
- Statyczny kontrakt instalatora potwierdza `SetupIconFile`, `WizardSmallImageFile`, `UninstallDisplayIcon` oraz numer `0.2.0`.
- GitHub Release ma tag `v0.2.0`, nazwę `QuickConvert v0.2.0` i wskazuje commit zawierający zmianę wersji.
- Release zawiera instalator i `SHA256SUMS.txt`; nazwy i sumy odpowiadają wynikowi workflow.
- `v0.1.0` pozostaje niezmienione.

## Poza zakresem

- Code Signing Authenticode.
- Publikacja w Microsoft Store, Chrome Web Store lub publicznym AMO.
- Zmiana logo aplikacji albo projektu interfejsu.
- Nadpisywanie lub usuwanie istniejącego wydania `v0.1.0`.
